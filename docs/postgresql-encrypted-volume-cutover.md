# Optional PostgreSQL 14 direct PGDATA bind-mount cutover

This is an optional operator runbook for a planned maintenance window, not an automated migration or a description of current production. The default `docker-compose.yml` uses published GHCR application images and Docker's `pgdata` named volume; its physical storage follows the host's Docker data root. Current production uses `console_pgdata` beneath `/mnt/volume_nyc3_1790759919647/docker` on the operator's encrypted 20 GB DigitalOcean Volume, with containerd beneath `/mnt/volume_nyc3_1790759919647/containerd`. It does not use this direct PGDATA bind mount or `--pg-volume`. See [current deployment facts](production-deployment.md#current-production-named-volume-on-encrypted-docker-storage) for configuration, firewall, transcript permissions, and backup details.

The remaining instructions apply only when deliberately choosing the optional direct bind mount. Do not combine this storage move with an application release or the first GHCR deployment: keep the currently deployed PostgreSQL, backend, and bot image IDs, and run pending migrations through the normal backend migration runner in a separate deployment after the storage cutover is stable.

For the commands below, export the exact already-deployed `CONSOLE_IMAGE_TAG` and preserve the existing Compose project name. If the server still runs legacy locally built images, perform the storage-only cutover using its existing deployed Compose configuration, then switch to GHCR in a separate release window. Do not select `latest` during the cutover. After the cutover, every application deployment must retain the Volume override: follow [Production deployment](production-deployment.md) and run `bash scripts/deploy-production.sh --pg-volume` with the path and recorded UUID exported. The script checks the mounted filesystem and PG14 data directory before pulling or starting services.

The target is one DigitalOcean Block Storage Volume attached to the production Droplet, with a PostgreSQL data directory directly beneath its persistent mountpoint. PostgreSQL remains in the `postgres:14` Docker container, with that directory bind-mounted to `/var/lib/postgresql/data`. DigitalOcean documents [Volume encryption at rest](https://docs.digitalocean.com/products/volumes/details/features/), [creation and mounting](https://docs.digitalocean.com/products/volumes/how-to/create/), [Volume snapshots](https://docs.digitalocean.com/products/snapshots/how-to/), and [the fact that Droplet backups exclude attached Volumes](https://docs.digitalocean.com/products/volumes/details/limits/).

## Preparation before the window

1. Identify the production Droplet, region, current Compose project/directory, and the actual `rotmg_db` container. Create and attach a sufficiently sized DigitalOcean Block Storage Volume **in the same region**. Format the new Volume only once, mount it on the Droplet, and configure a persistent mount using the provider's instructions. Record its device identity, filesystem UUID, `findmnt` source, and mountpoint. Check that the mount survives a reboot before the cutover. Never format a device containing data.
2. Create an empty `pgdata` directory **on the mounted Volume**. Set `CONSOLE_PGDATA_HOST_PATH` to its absolute path, with the Volume mountpoint as its direct parent. Do not create that child directory on Droplet-local storage. The opt-in override uses `${CONSOLE_PGDATA_HOST_PATH:?...}` and `create_host_path: false`; a missing path makes Compose fail. A bare existing mountpoint can still exist when the Volume is detached, so verify `mountpoint` and `findmnt` every time before starting PostgreSQL.
3. Record the running container image IDs (`docker inspect rotmg_db rotmg_backend rotmg_bot --format '{{.Name}} {{.Image}}'`), `docker exec rotmg_db postgres --version`, the current `/var/lib/postgresql/data` mount source from `docker inspect`, `PG_VERSION`, `docker exec rotmg_db id postgres`, and approximate size. Check whether `pg_wal` or any `pg_tblspc` entry is a symlink outside PGDATA; those targets require a separate plan before proceeding. Set `CONSOLE_EXPECTED_VOLUME_UUID` to the filesystem UUID recorded from the attached Volume, then run `bash scripts/pg-volume-preflight.sh` with both that and `CONSOLE_PGDATA_HOST_PATH` exported. The read-only script checks the mountpoint and UUID and reports the `findmnt` source. Compare that source with the recorded DigitalOcean device; a mountpoint alone does not prove the right device is attached.
4. Record representative table row counts, database names, and migration history from the current DB. Choose stable tables such as `guild`, `member`, `run`, `verification_session`, and `ticket_transcript_event` **only if present** in the currently deployed schema. Record `SELECT version();` and `SELECT * FROM _migrations ORDER BY filename DESC LIMIT 10;`. Keep the before/after queries identical.
5. Create a recovery logical backup **directly on the mounted encrypted Volume**, for example `docker exec rotmg_db pg_dump -U postgres -Fc rotmg_raids > "$VOLUME_MOUNT/rotmg_raids-before-cutover.dump"`, plus `pg_dumpall -g` for roles/globals where needed. Check exit status, file size, and `pg_restore --list`; if possible, restore it to an isolated PG14 test database and verify representative data. Ensure the Volume has capacity for both the backup and full cold copy. A dump is not a substitute for preserving the old Docker volume.
6. Confirm no new application image will be built or pulled in this window. Check `docker compose -f docker-compose.yml -f docker-compose.pg-volume.yml config` with `CONSOLE_PGDATA_HOST_PATH` set, and verify the merged `db` mount is **one bind mount** to `/var/lib/postgresql/data` with the expected source and `create_host_path: false`. The override is selected only with both `-f` arguments; ordinary `docker compose up` remains on `pgdata`. Run `scripts/pg-volume-preflight.sh` again immediately before the stop.

## Maintenance window

Use the same Compose project name and directory throughout. Keep the bot/backend images at the exact IDs recorded above; resolve any mismatch before starting. Do not pull or build unrelated images. The backend image starts its migration runner, so it must be the same deployed image with no pending migrations for this storage-only window.

1. Announce maintenance and block new writes. Stop the bot, then backend, then PostgreSQL cleanly, for example `docker compose stop bot`, `docker compose stop backend`, `docker compose stop db`. Confirm `rotmg_db` is actually stopped with `docker inspect`; do not copy final PGDATA from a running PostgreSQL server.
2. Recheck `mountpoint -q "$VOLUME_MOUNT"`, `findmnt --target "$VOLUME_MOUNT"`, the recorded device identity, and that the destination `pgdata` directory is empty and on that mount. If any check fails, leave PostgreSQL stopped and fix the mount. Do not start against an unmounted directory.
3. Cold-copy the **complete contents** of the old Docker volume mount source into the destination. Use `rsync -aHAX --numeric-ids "$OLD_PGDATA_SOURCE/" "$CONSOLE_PGDATA_HOST_PATH/"` as root so numeric UID/GID, permissions, hardlinks, ACLs, and xattrs are preserved. Do not use `chmod 777` or copy only selected PostgreSQL files.
4. Compare source and destination with a read-only check such as `rsync -aHAXnci --numeric-ids "$OLD_PGDATA_SOURCE/" "$CONSOLE_PGDATA_HOST_PATH/"` (no output means no differences in source files/metadata), and check `PG_VERSION` is `14`. Inspect any extra destination entries. Keep the original Docker volume untouched.
5. Export the destination path in the operator shell and select **both** Compose files: `docker compose -f docker-compose.yml -f docker-compose.pg-volume.yml up -d --no-build --pull never --no-deps db`. First inspect the resolved config and mount again. Start **only PostgreSQL**, then wait for `pg_isready`, check logs and `SELECT version();`. If the expected Volume is not mounted, stop here; never allow PostgreSQL to initialize a fresh local data directory.
6. Start backend with the same selected files and existing image, verify health and a historical read, then start bot. Use `--no-build --pull never` and `--no-deps` for the service starts so Compose does not replace an already checked database container. Do not combine this with application changes or migration 079/other pending migrations.

Never run `docker compose down -v`, remove the old volume during cutover, use `chmod 777`, or take the final copy while PostgreSQL is running.

## Verification

- `docker inspect rotmg_db` shows exactly one bind mount at `/var/lib/postgresql/data`, sourced from `CONSOLE_PGDATA_HOST_PATH`; `findmnt` shows that path's parent on the recorded DigitalOcean device.
- PGDATA `PG_VERSION` is `14`; server version is 14; `rotmg_raids` exists; migration history and representative table counts match the recorded values; historical Console records are readable.
- Perform one controlled new write through Console, read it back, restart the PostgreSQL container, and read it back again. Verify backend and bot recover normally.
- In a separately planned restart/reboot check, verify the Volume mounts before Docker/Compose can start PostgreSQL. If boot ordering does not enforce this, add a host service dependency or operational start gate before enabling automatic restart. `create_host_path: false` prevents a missing child directory from being created, but does not prove that an existing directory is on the correct device.

## Rollback

Before accepting any new production writes on the Volume-backed DB: stop bot, backend, and new PostgreSQL; restore the original Compose mapping by using **only** `docker-compose.yml`; start the original Docker `pgdata` PostgreSQL container with the recorded image; verify its database and representative counts; then restart the original backend and bot images. Do not delete the new copy while investigating.

Once new writes have been accepted, the original `pgdata` database is stale. Blind rollback to it would lose those writes. Stop and design a data reconciliation/recovery plan instead.

## Backups and later cleanup

After migration, schedule PostgreSQL logical dumps written onto encrypted storage, with a globals dump where roles/tablespaces require one. Take periodic DigitalOcean **Block Storage Volume snapshots** and periodically restore a dump or snapshot to an isolated PostgreSQL 14 instance to prove recoverability. Use consistent PostgreSQL backup practices for live databases; a live filesystem copy alone is not a valid database backup. Normal DigitalOcean Droplet backups do **not** include the attached Volume and are not the database backup.

For installations performing this optional cutover, only after stability and restore verification, inventory the old Docker `pgdata` volume, temporary dumps, temporary file copies, old Droplet snapshots, old DigitalOcean Droplet backups, and manually created backups. Their removal is a **manual owner decision** after retention and recovery needs are reviewed. No cleanup command is automated here. The operator reports that the former production Droplet and its old snapshot have already been destroyed; this generic runbook does not imply they still exist.
